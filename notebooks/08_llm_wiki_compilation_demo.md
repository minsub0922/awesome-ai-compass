# 08: LLM Wiki Compilation — 강의 보조 자료

> **핵심 메시지**: LLM은 질문에 답하는 봇이 아니라, 흩어진 지식을 구조화된 자산으로 합성하는 편집 엔진이다.

---

## 섹션 개요

| # | 섹션 | 핵심 개념 | 드라마틱한 포인트 |
|---|------|-----------|-----------------|
| 1 | 소스 로드 | 다양한 타입의 소스를 모은다 | 타임라인 차트: 2022~2024, archived 소스 시각적 분리 |
| 2 | 소스 분석 | 다양성이 위키 품질을 결정한다 | archived 소스가 자동 감지됨 |
| 3 | Wiki 컴파일 | LLM이 편집자 역할 | 파이프라인 다이어그램: 소스 6개 → LLM → 위키 7섹션 |
| 4 | 품질 체크 | 좋은 위키의 3가지 조건 | 인용 매트릭스: ✓가 골고루 분포 = 합성의 증거 |
| 5 | 점진적 업데이트 | 전체 재컴파일 없이 섹션만 갱신 | 새 논문 1개 → 영향 섹션만 자동 식별 + 업데이트 |

## 섹션 1. 소스 로드

**무엇을 하는가?**  
"프롬프트 엔지니어링"에 관한 6가지 소스를 로드한다.

**왜 이 6가지인가?**

| 소스 타입 | 예시 | 역할 |
|-----------|------|------|
| 📄 학술논문 | CoT 논문 (2023) | 이론 근거, 재현 가능한 수치 |
| 📘 공식문서 | OpenAI 가이드 (2024) | 현재 권장 방법 |
| 📝 엔지니어링블로그 | Anthropic 블로그 (2024) | 실전 경험, edge case |
| 💬 커뮤니티FAQ | 커뮤니티 (2024) | 흔한 오해 커버 |
| 📊 벤치마크 | 성능 보고서 (2024) | 기법별 수치 비교 |
| 📦 **아카이브** | GPT-3 가이드 (2022) | **직접 채택 금지** — 구버전 주의 섹션에만 등장 |

**강조 포인트**: 아카이브 소스는 흐릿하게 표시된다 → "이 정보는 쓸 수 없다"는 것을 시각적으로 인지.

---

## 섹션 2. 소스 분석

**무엇을 하는가?**  
로드된 소스의 타입 분포, 날짜 범위, archived 여부를 분석한다.

**왜 중요한가?**  
편집자가 쓰기 시작하기 전에 재료를 파악하는 과정.  
시간 범위가 2년 이상이면 충돌 가능성이 있고, archived 소스가 있으면 별도 처리가 필요하다.

```
소스 타임라인: 2022-06-01 ~ 2024-10-15 (약 2년)
→ GPT-3 시대 가이드와 현재 가이드가 공존 = 충돌 발생 가능
```

---

## 섹션 3. Wiki 컴파일 ← 가장 중요

**무엇을 하는가?**  
LLM에게 Wikipedia 편집자 역할을 맡겨 7개 섹션으로 구성된 위키 초안을 생성한다.

### 편집자의 5가지 책임

```
① 전체 소스 읽기     — 6개 문서를 모두 읽는다
② 충돌 해결          — current + 최신 날짜 기준으로 결론
③ 섹션 구조화        — 예측 가능한 7섹션 형식 유지
④ 인용 달기          — 모든 주장에 [출처: DOC-ID] 표시
⑤ 구버전 격리        — archived는 섹션 6에만 등장
```

### 위키 섹션 구조

```markdown
## 1. 개요
## 2. 주요 기법
## 3. 실전 적용 가이드
## 4. 기법별 성능 비교
## 5. 흔한 실수 & 주의사항
## 6. 구버전 가이드 주의   ← archived 소스는 여기만
## 7. 참고 문서
```

### RAG와의 결정적 차이

```
RAG      질문 → 검색 → 답변 → 사라짐
LLMWiki  소스 → 편집 → 위키 → 남음 (재사용)
```

**강조 포인트**: 파이프라인 다이어그램을 보여주면서  
"모델이 6개를 다 읽고 하나로 합쳤다, 이게 편집이다" 언급.

## 섹션 4. 품질 체크

**무엇을 하는가?**  
생성된 위키가 3가지 조건을 만족하는지 자동 검증한다.

### 좋은 위키의 3가지 조건

| 조건 | 판단 기준 | 미충족 시 |
|------|-----------|-----------|
| 구조 완결성 | 7개 섹션이 모두 존재하는가? | 프롬프트에 섹션명 명시 필요 |
| 인용 표시 | `[출처:` 가 텍스트에 있는가? | 프롬프트에 인용 규칙 강화 |
| 구버전 분리 | archived 내용이 섹션 6에만 있는가? | 편집 규칙 재검토 |

### 인용 매트릭스로 합성 증거 확인

```
        PAPER  OPENAI  BLOG  FAQ  BENCH  ARCHIVE
1.개요    ✓      ✓
2.기법    ✓      ✓      ✓
3.가이드         ✓      ✓     ✓
4.성능    ✓                        ✓
5.실수                       ✓
6.구버전                                  ✓
7.참고    ✓      ✓      ✓     ✓    ✓      ✓
```

**강조 포인트**: ✓가 골고루 분포되어 있다 = LLM이 단순 복사가 아닌 다중 소스 종합을 했다는 증거.  
특히 ARCHIVE 열의 ✓가 6번 행에만 있으면 구버전 격리가 성공한 것.

## 섹션 5. 점진적 업데이트

**무엇을 하는가?**  
새 논문(Self-Refine)이 등장했을 때, 전체 재컴파일 없이 영향받는 섹션만 업데이트한다.

### 왜 이게 중요한가?

Wikipedia는 한 번 쓰고 끝나지 않는다.  
LLMWiki도 마찬가지 — 새 정보가 들어오면 전체가 아닌 관련 섹션만 갱신한다.

### 업데이트 흐름

```
새 논문 입력
    ↓
LLM: "이 논문이 영향하는 섹션은?" → JSON 응답
    ↓
영향 섹션만 식별: [## 2. 주요 기법, ## 4. 기법별 성능 비교]
    ↓
해당 섹션만 갱신 (나머지 5개 섹션은 그대로)
    ↓
참고 문서 섹션에 새 소스 자동 추가
```

**강조 포인트**:  
"7개 섹션 중 2개만 업데이트했다. 나머지 5개는 손대지 않았다.  
이게 가능한 이유는 섹션이 구조화되어 있기 때문이다."

## 섹션 6. RAG vs LLMWiki 비교

**무엇을 하는가?**  
동일한 질문 3개에 두 방식으로 답하고 결과를 나란히 비교한다.

### 비교 질문

1. Chain-of-Thought는 항상 효과적인가?
2. few-shot 예시는 많을수록 좋은가?
3. 수학 문제 풀 때 어떤 기법이 가장 좋은가?

### 두 방식의 차이

| 항목 | RAG | LLMWiki |
|------|-----|---------|
| **목적** | 지금 질문에 답하기 | 다음에도 쓸 지식 자산 만들기 |
| **출력** | 1회성 답변 | 구조화된 위키 문서 |
| **지속성** | 없음 (매번 재생성) | 있음 (점진적 업데이트) |
| **일관성** | 실행마다 다름 | 항상 동일한 구조 |
| **충돌 처리** | 즉흥적 | 명시적 해결 + 구버전 섹션 |
| **출처** | 응답 안에 묻힘 | 섹션별 명시적 인용 |
| **비용** | 질문마다 검색+생성 | 컴파일 1회 → 이후 조회만 |

### 언제 어떤 걸 쓰는가?

```
RAG가 맞는 경우:
  - 질문이 다양하고 예측 불가능할 때
  - 최신 문서를 즉시 반영해야 할 때
  - 코퍼스가 자주 바뀔 때

LLMWiki가 맞는 경우:
  - 같은 주제를 팀이 반복적으로 참조할 때
  - 일관성 있는 답변이 중요할 때 (고객 응대, 온보딩)
  - 지식을 자산으로 축적하고 싶을 때
```

## 전체 흐름 요약

```
[소스 6개: 논문, 공식문서, 블로그, FAQ, 벤치마크, 아카이브]
            ↓
      소스 분석 (타입 분포, 날짜 범위, archived 식별)
            ↓
   LLM 편집자 (충돌 해결 + 섹션 구조화 + 인용)
            ↓
      위키 초안 (7섹션, 각 섹션에 [출처: DOC-ID])
            ↓
   품질 체크 (구조 완결성 + 인용 + 구버전 격리)
            ↓
  점진적 업데이트 (새 소스 → 영향 섹션만 갱신)
            ↓
  재사용 가능한 지식 자산 ← 이게 LLMWiki의 목표
```

## 강의자 체크포인트

  "6개를 다 읽고 7개를 만들었다. 이게 편집이다."

- **섹션 4 (품질 체크)**: 인용 매트릭스에서 ARCHIVE 열 강조.  
  "빨간 테두리 열의 ✓가 6번 행에만 있으면 구버전 격리 성공."

- **섹션 5 (점진적 업데이트)**: "전체 재컴파일 없이 2개 섹션만 바꿨다"에서 잠시 멈추기.

- **섹션 6 (비교)**: RAG 답변과 LLMWiki 답변을 나란히 보여주면서  
  "RAG는 그때그때, Wiki는 항상 같은 구조"를 체감시키기.
